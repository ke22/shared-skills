# Audience Deck Skill

把一份研究內容，依「這次是講給誰聽」重新取捨、重新框架，並用固定的 house style 建構。
核心假設：**內容是同一個 bank，聽眾決定選哪些、先講哪個、砍掉哪個。**

## Load model（沿用 workspace 慣例）

- 本檔（SKILL.md）：精簡、進場即讀。工作流 + 聽眾快速路由 + 產出規則都在這。
- `references/audience-playbook.md`：**按需載入**。鎖定聽眾後才讀，取得完整 reweight 指令。權威版本——與下方速查表衝突時以此為準。
- `references/house-style.md`：**按需載入**。要建構或改版面時才讀，取 design tokens 與版型。
- `references/rubric.md`：**改版時載入**。每次修改 SKILL.md 後跑一次自評，<3.5 分先修再用。

## 核心原則

1. **內容先於版面。** 論證沒收斂前不碰配色。順序永遠是 論證 → 資料 → 版型 → 美感。
2. **一頁一主張，標題是句子不是標籤。** 「失智照護需求持續擴大，但既有支援難以轉化為當下行動」而非「研究背景」。句子本身要能獨立成立——不加「（交付物清單）」「（風險預警）」這類括號分類尾綴，也不用「· 為什麼重做」這種反問句掛在 kicker 後面；分類或理由該講的話，直接寫進句子或核心訊息（見 Phase 3、house-style.md 一致性硬規則）。
3. **Ghost-deck test。** 只把每頁 action title 串起來讀，要能講完整個論證；不行就改結構，不是改版面。
4. **聽眾決定取捨。** 同一份 bank，對不同聽眾砍/留/加/換序都不同。鎖定聽眾前不要出大綱。
5. **House style 一致。** 所有頁面共用同一套 tokens 與版型骨架（見 house-style.md）。

## Workflow

### Phase 1 — 盤點素材，建 content bank
把手上的素材（既有 deck、訪談、資料、逐字稿）拆成可重組的原子：
- **claims**：每個可當 action title 的主張句
- **quotes**：受訪者原話（標受訪者代號，如 I01 照護講師 / P02 居服員）
- **exhibits**：圖表、流程圖、mockup、統計數字（如 36.5 萬人、90.9%）
- **citations**：文獻（保留原格式，永遠放頁底灰字）
不要在此階段就摘要或刪減——先看清全部有什麼。

**使用者指定 URL 時（例如 LLM wiki 頁面、線上文件）**：視為權威素材來源，動手 fetch 該 URL、把內容拆進上述四類原子，權威層級等同「既有 deck」——不要只憑記憶推測內容，也不要因為是外部連結就跳過不處理。fetch 失敗（連不上、需要登入、頁面消失）時，明講「這個 URL fetch 失敗」，把對應素材標記「待補」，比照下面「素材不齊」edge case 處理，不要假裝沒看到這個 URL、也不要憑空捏造內容補上。

### Phase 2 — 鎖定聽眾（**必做，出大綱前**）
先從情境判讀（線索：誰會在現場、這份東西講完之後要拿去做什麼決定、對方怎麼稱呼這場會議——「進度會議」「demo」「口試」本身就是答案），
再向使用者確認一句：「這次是給 ___ 看、目的是讓他們 ___，對嗎？」
確認後才讀 `references/audience-playbook.md` 取得該聽眾的：主打鉤子 / 壓縮項 / 加強項 / 地雷 / 時間預算 / scaffold。

### Phase 3 — 選 claims、定結構，交給 tw-presentation-writing 產文案
依聽眾的 reweight 指令，從 bank 選 claims、決定逐頁順序與骨架（每頁大致要講什麼、佐證是什麼、exhibit 用哪個版型）——這是 `audience-deck` 自己的判斷，不假手他人。
**選定之後，把「選定的 claims + 聽眾 profile（已知／在乎／地雷／時間預算，見 audience-playbook）」交給 `tw-presentation-writing`，由它產出實際逐頁文案**（action title 斷言句、bullet 文字）；`audience-deck` 不自己寫最終文案，只提供草稿層級的結構讓 `tw-presentation-writing` 有依據可寫。回報時明講已把這批 claims 交給 `tw-presentation-writing` 處理文案。
輸出格式（結構層，文案細節由 `tw-presentation-writing` 填）：
```
## Slide N: [主張句]
- 佐證/證據 1（至多三點）
- exhibit：[版型名，見 house-style.md]
- citation：[若有]
transition：[如何接下一頁]
```
`[主張句]` 最終要是完整、可獨立朗讀的斷言句，不加「（XX清單）」「（XX預警）」這類括號分類註記——真實失敗案例：「## Slide 5 — 我們會交出哪些東西（交付物清單）」，括號是贅字，唸出來會卡，拿掉不影響理解。**核心訊息寫進 `main-title`**（見 house-style.md「標題骨架」章節——`sec-title` 短主題標籤＋`main-title` 斷言句兩層搭配，字級與規格已依真實成品 deck 校正過）；句子要跟 action title 同等分量的斷言，不是反問句或條列標籤。這些文案品質標準是講給 `tw-presentation-writing` 聽的交付要求，不是要 `audience-deck` 自己動筆改寫。
`tw-presentation-writing` 交回文案後，串讀所有 title → 論證是否完整？不完整就先修結構（回到選 claims / 定順序這一步），不是回頭自己改文案措辭。

### Phase 4a — Lofi Wireframe 預覽（必做，建構前）

`tw-presentation-writing` 交回文案、Phase 3 的 ghost-deck test 通過後，動手進 Phase 4 建構前，先把整份 deck 逐頁畫成 lofi wireframe，一次全部秀出來，再問使用者一句確認——不要跳過直接進 Phase 4 的資料夾掃描或寫檔。

**格式（所有版型共用同一個框，不分版型另外設計）**：
```
┌─ Slide N ── {slide-nav: 頁碼/階段} ────────────────────┐
│ sec-title:   {sec-title 文字}                            │
│ ▌main-title: {main-title 文字}                            │
│                                                          │
│ 版型: {house-style.md 版型庫裡的版型名稱}                  │
│  內容摘要: {一句話摘要，不是逐字複製 bullet/表格內容}       │
│                                                          │
│ citation: {有／無}（{citation 文字，若有}）                │
└──────────────────────────────────────────────────────┘
```
不管是三卡並列、推導對照表、字母卡橫列、代辦檢核清單……house-style.md 版型庫裡的 12 種版型都用這同一個框，只換「版型」那一行的名稱跟內容摘要，不要為特定版型另外設計框線或排版——這是刻意的簡化，目的是檢查「版型選得對不對」，不是預覽精確排版比例（精確排版留給真正的 Phase 4 build）。

**內容摘要一律是摘要，不是複製**：例如推導對照表有 7 列比較，摘要寫「7 列比較（對象/篩選/期間/資料/分析/樣本量/用量）」，不要把整張表的文字貼進 wireframe——逐字內容在 Phase 3 已經跟 `tw-presentation-writing` 定案過一次，這裡只檢查版型跟內容搭不搭，不是重複校對文案。

**一次全部秀出來，只問一次**：不管 deck 有幾頁（這個 skill 常見的 deck 落在 7–23 頁），所有頁面的 wireframe 一次全部顯示在同一則回覆，結尾只問一句「這樣的版型與內容安排可以進入下一步建構嗎？」——不要逐頁停下來個別確認，那對長 deck 太慢。

**使用者說有問題時，回 Phase 3 改，不要在這裡直接改**：如果使用者指出某頁版型不對、順序怪、或內容跟版型不搭，回到 Phase 3 重新選 claims/版型，改完再重新跑一次這個 wireframe 預覽、問一次確認——不要在這個 phase 裡直接動手改版型或文案。

**預設一定做，使用者明講跳過才跳過**：這個 gate 預設一定執行；只有使用者明講「不用預覽，直接建」之類的話才跳過，跳過時要在回覆裡明講「已跳過 wireframe 預覽（使用者要求）」，不要悄悄略過不提。

### Phase 4 — 選版型並建構
**先掃現有簡報、對齊當前模板，再讀本檔 tokens**（house-style.md §0，跟 §0.5 輸出資料夾判定順序同一套邏輯：使用者指定資料夾 > 專案既有 deck 資料夾 > workspace 預設資料夾 `/Users/yulincho/Documents/01_Github/audien-deck`）：依序掃這三個位置，取找到的最近修改 `.html` 成品 deck，沿用它的 `:root` tokens 與元件——即使找到的成品是在 workspace 預設資料夾、不是這次專案自己的資料夾，一樣視為權威樣式來源，不要跳過。三個位置都沒有成品時，本檔 tokens 才當 fallback，衝突時以找到的現有成品為準並回頭同步 house-style.md。
接著讀 `references/house-style.md`，為每頁挑版型（三卡 / 大數字 / 循環流程 / 痛點卡 / 對照表 / mockup+清單 / 綠勾 vs 紅叉 / 全幅圖）。
**動手寫檔前，先列出目標輸出資料夾現有檔案**（實際跑一次列目錄操作，不要憑記憶或假設），把列出的結果直接寫進回報——版號與是否要 archive，都要依這份實際列表判斷，不能憑印象決定。**目標資料夾判定順序**：使用者明講的資料夾 > 專案內既有成品 deck 所在資料夾（掃描得出）> workspace 預設輸出資料夾 `/Users/yulincho/Documents/01_Github/audien-deck`（跨專案通用的固定位置，找不到專案內既有 deck 時直接用這裡，不用先問）> 連這個位置都不合適時，動手寫檔前先問使用者放哪裡，不要自己另外決定路徑。
**版本號、命名、archive 規則一律以 `references/house-style.md` §0.5 為準**——本節不重複列規則本體，只重申動作順序：先列目錄 → 依 §0.5 規則推算版號 → 才寫檔。
產出優先為 **HTML deck**（單檔、inline CSS/JS、用 tokens）；若使用者要 .pptx，交棒官方 pptx skill，tokens 直接對映。

### Phase 5 — 結構 QA（ghost-deck test + 口說測試），不重寫文案
`tw-presentation-writing` 交回的文案已經處理過逐句品質（砍套話、砍假平行、砍標籤尾綴等文案層級規則屬於它的職責，不在這裡重複做）。`audience-deck` 在這個 phase 只做**結構層**檢查：
- **Ghost-deck test**：把所有 action title 串起來讀，論證是否完整、順序是否合理；不完整就回 Phase 3 調整 claims 選擇與順序，不是自己動手改寫某一句的措辭。
- **假平行結構檢查**：是不是每頁都剛好三點、每個 bullet 都同一句型時態這種結構性的假平行——如果是，回饋給 `tw-presentation-writing` 重寫，不要自己代寫。
- **口說測試（把關，非重寫）**：每句 title 唸出聲，若明顯像新聞稿或顧問報告，標記出來交還 `tw-presentation-writing` 調整；標準——「這句話你會當面講給你尊重的人聽嗎？」
- 若 `tw-presentation-writing` 回來的文案仍有標籤尾綴（「（XX清單）」「（XX預警）」）或反問句 kicker 殘留，視為文案沒達到 Phase 3 交付的品質標準，退回去請它重寫，而不是在這裡直接刪改。

## Edge Cases

- **素材不齊**（例如只有半份 deck、沒有原始訪談逐字稿）：在 Phase 1 明講缺什麼，用現有素材先建 bank，缺口標記為「待補」而非憑空生成 quote 或數字。
- **聽眾身份重疊**（例如「教授同時也是這場的評審之一」）：不要硬選一種路由，改成向使用者確認優先序——「這場主要目的是進度確認還是通過審查？」目的決定 scaffold，重疊的身份只影響用詞的正式程度。
- **聽眾不在三個既有路由內**（例如要講給投資人聽）：不要勉強套用最接近的一種。先問使用者這個新聽眾的「已知／在乎／地雷」三項（同 audience-playbook 欄位結構），現場生成一列新路由，事後補進 audience-playbook.md 成為第四種。
- **Bank 為空或素材是全新主題**（還沒有像 v5 這樣的既有 deck）：Phase 1 改成訪談使用者取代「拆解既有 deck」，其餘 Phase 2–5 流程不變。
- **聽眾在會議前臨時改變**（例如原訂教授，改成教授+業界一起聽）：視為新的 Phase 2，重新走一次鎖定流程；不要在舊 outline 上直接增刪，避免論證斷裂。
- **砍掉某頁後，其他頁面留下斷鏈引用**（真實案例：砍掉定義「指標一/二/三」編號的頁面後，後面頁面的表格還在寫「指標二」「指標三」，讀者已經無從查起這編號是什麼）：刪頁前，先搜一次全文有沒有其他頁引用該頁定義的術語/編號/縮寫；刪完後，把殘留引用改寫成不依賴該定義也看得懂的白話（或把定義搬到第一次用到的那頁），不要留著編號當作「反正大家知道」。同理，改寫某頁標題去歸納多個並列項目時（例如「先補 4 項」），要逐項核對來源，不要用其中一項的名稱（如「DK2」）概括全部，只有真的全部項目都對應同一件事時才能共用同一個標籤。

## 聽眾快速路由（速查用，權威版本在 audience-playbook.md）

| | 指導教授 | 工作方聽眾 | 研討會評審委員 |
|---|---|---|---|
| 他們已知 | 全知，跟過全程 | 懂實務痛點、不懂學術脈絡 | 懂研究方法、不懂你的專案 |
| 最在乎 | 論證是否站得住、貢獻定位、缺口與下一步 | 實際痛點、產品能做什麼、落地價值 | 文獻缺口、方法正當性、效度與限制 |
| 可壓縮 | 背景動機、方法細節（口頭帶過） | RtD / 紮根理論 / 文獻 / 評估方法論 | 產品操作細節、實作技術棧 |
| 需加強 | 設計知識產出、V6 規劃、自我批判 | Demo、痛點共鳴、市場數字、應用場景 | 抽樣正當性、資料飽和、三軸比對效度 |
| 開場鉤子 | 直接進度：「上次之後我把 X 收斂成…」 | 情境痛點：「照護者半夜遇到這種狀況…」 | 文獻缺口：「現行 chatbot 研究缺真實場域視角」 |
| 主要地雷 | 過度 rehearse 背景浪費時間 | 太多學術術語會失去房間 | 把形成性評估講成成效驗證會被電 |
| scaffold | Report-Out / 進度深談 | The Case（近 The Pitch） | Structured Argument（SCR） |

## Claude Code Slash Command

`.claude/commands/deck.md` 已實作，一句話切聽眾，見該檔案。用法：

```
/deck advisor    → 讀本 skill + playbook「指導教授」段 → 產進度深談版 outline
/deck industry   → 產 demo 導向、砍方法論的落地版 outline
/deck committee  → 產嚴謹學術版 outline，Q&A 防守清單一併輸出
/deck [新聽眾]   → 走 Edge Cases 的「聽眾不在既有路由內」流程
```
